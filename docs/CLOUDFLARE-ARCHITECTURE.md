# ASAS Business Suite — Cloudflare-first architecture (2026-11-02)

**Decision:** No Supabase in the new ASAS Business Suite. The earlier V4/V5 Supabase Postgres/Auth backend starter is **superseded** and must not be deployed or connected.

## Logical topology

Browser / responsive React UI → Cloudflare Workers (API / authentication / authorization)
- ASAS Core + CRM → Cloudflare D1 (SQLite)
- Signed/controlled file delivery → Cloudflare R2
- Notifications and cross-system sync → Cloudflare Queues / scheduled Workers
- Concurrency-critical state → Durable Objects where actually required
- ERP integration gateway → dedicated ERPNext/Frappe site(s) on separately managed infrastructure (MariaDB required)
- Platform operations/admin → separate platform identity and audit boundaries

The GitHub Pages frontend remains a **demo only**. Commercial hosting should use Cloudflare Workers Static Assets with secured Worker API.

## Authentication and authorization

Cloudflare infrastructure **does not automatically provide full customer registration, recovery, organization membership, or field-level SaaS permissions**. A suitable open-source identity/authentication library (Better Auth with a validated D1/Workers adapter is a candidate) needs an implementation and security review. Strong password hashing / passkeys or SSO, email verification, MFA for administrators, session revocation, CSRF protections, rate limits and auditability are required before launch.

Cloudflare Access can gate internal ASAS administrative services, but should not be confused with the complete multi-tenant application identity and permission engine.

D1 is SQLite and does **not** implement PostgreSQL RLS. The Worker must obtain user identity from a validated server-side session, resolve membership from D1, then enforce both action permissions and row/branch/organization filters for every read/write. Never trust client-supplied organization IDs, roles or permissions. Test broken object-level authorization, role escalation, cross-tenant record guessing and data export. Use parameterized prepared statements.

For initial staging, a shared D1 database can contain explicit `organization_id` foreign-key scopes. At larger scale, use separate D1 databases per tenant or tenant tier to reduce blast radius and avoid throughput limits. Always keep a separate global platform metadata database and distinct audit trails.

## Data model

`cloudflare/migrations/0001_core.sql` is a **starter schema only** with:
- organizations / memberships / role grants
- CRM accounts and contacts scoped to organizations
- append-only audit log (application policy enforced)
- centrally managed global ad campaigns with an active-paid cap of five

The house ad is generated by the Worker when no paid active campaigns are found, not a paid campaign row. Never use R2 public write access for advertiser content. Approval, scanning, moderation, signed object access and media transcoding are separate steps.

## ERP and accounting

ERPNext is not simply interchangeable with D1 and needs an operational Frappe/ERPNext deployment and MariaDB. We continue the **hybrid architecture** with a separate ERP host, one ERP site per subscribing company when justified. Credentials are held only in the Worker secret store; ERP actions pass through a service backend. Use idempotent events/outbox for CRM-to-ERP sales transitions.

## Limits and risk

- D1 database size is limited (currently 10 GB per database on Workers Paid, 500 MB on Free); storage must be planned per company / tier.
- An individual D1 database serializes queries; a large unified database can become a bottleneck.
- Free D1 daily row limits are enforced; pricing and quotas must be reviewed before customer onboarding.
- Complex general-ledger transaction validation remains in ERPNext, not in a home-built D1 accounting core.
